# Roastory - магазин свежеобжаренного кофе

Каталог кофейных лотов, корзина и оформление заказа с расчётом итоговой суммы на сервере.

[Открыть проект](https://memorim.github.io/roastory-coffee-shop/)

<img src="docs/mobile.png" width="320" alt="Мобильная версия">

## Возможности

- Фильтрация кофе по обработке, выбор количества и корзина.
- Сохранение заказа и его позиций в SQLite.
- Фотографии кофе и обжарки, адаптивные карточки и локальные изображения.

## Стек и устройство

JavaScript, Express, Zod, встроенный SQLite в Node.js и HTML/CSS.

## Ключевые решения

- Цена загружается из серверного каталога. Заказ и его позиции сохраняются одной транзакцией.
- Параметры проходят серверную валидацию, ошибки JSON возвращают ограниченный ответ. По умолчанию API слушает loopback.
- Чтение цен и запись заказа находятся внутри `BEGIN IMMEDIATE`. Цены - целые рубли, допустимы значения 1-1 000 000; итог проверяется на безопасное целое. Клиентская цена игнорируется. В заказе до 50 разных лотов, по 1-10 единиц каждого.
- Необязательный `Idempotency-Key` сохраняет результат заказа: повтор с теми же данными возвращает прежний ID и сумму; другие данные с тем же ключом дают 409. Форма сохраняет ключ и корзину при сетевой ошибке.
- Ответ просмотра заказа содержит только ID, сумму, статус и дату; имя и email не возвращаются. Ошибки не пишут контакты в журнал.

## Локальный запуск

Node.js 24.18.0 и pnpm 11.7.0; версии закреплены в файлах проекта.

```bash
npm install --global pnpm@11.7.0
pnpm install --frozen-lockfile
pnpm start
```

Откройте `http://localhost:4500`. HOST ограничен loopback, API проверяет Host и Origin. Для разработки доступен `pnpm dev`.

## Настройки

Параметры перечислены в [.env.example](.env.example). `pnpm start` использует окружение процесса и не загружает файл автоматически. После копирования `.env` его можно загрузить явно: `node --env-file=.env server.js`.

## Данные и обновления

SQLite хранится в `data/roastory.db`. Транзакционное обновление добавляет nullable поля request_key/request_hash и уникальный индекс, сохраняя прежние заказы и позиции. Перед обновлением сохраните резервную копию; удалять БД вместо миграции не нужно.

## Проверки

```bash
pnpm test
pnpm test:contract
pnpm test:upgrade
pnpm audit --audit-level=high
pnpm exec playwright install --with-deps --only-shell chromium
pnpm test:e2e
```

Проверяются границы количества, дубли SKU, цена сервера, откат заказа и позиций, приватность ответа и две независимые серверные копии с одной SQLite и одним ключом. Upgrade сохраняет прежний заказ с позициями. Браузерные проверки покрывают каталог, корзину, повреждённое хранилище и потерю ответа. Playwright - только зависимость разработки, чтобы эти сценарии выполнялись в CI.

Браузерные проверки запускают отдельную SQLite в памяти и не используют обычную папку `data`.

CI устанавливает зависимости по зафиксированным версиям и запускает настроенные проверки. Отдельная проверка документации находит неверные локальные ссылки и изображения. Проверка уязвимостей учитывает известные проблемы на момент запуска.

## Ограничения

- Подключён тестовый магазин ЮKassa; создание платежа и серверная проверка статуса проверены на тестовом сервере. Успешная оплата пока не подтверждена сквозным сценарием. Реальные платежи запрещены; доставка исключена из задачи. Полноценные аккаунты покупателей не реализованы, доступ к заказу предоставляется по индивидуальному ключу.
- Публичный режим требует HTTPS и ключ владельца; кабинет владельца защищён, покупатель читает только заказ со своим ключом. Для постоянного размещения необходима сохраняемая БД. JSON ограничен 16 КБ; 20 попыток заказа в минуту сохраняются в SQLite и разделяются процессами.
- Клиенты без Idempotency-Key по совместимости создают новый заказ на каждый POST. Контакты автоматически обезличиваются через CONTACT_RETENTION_DAYS (90 дней по умолчанию, проверка раз в час при API-запросах); остатки проверяются и списываются атомарно. Стоимость фиксируется при создании заказа; интерфейсная сумма предварительная.

## Версия в браузере

Открывается без установки. Изменения изолированы в памяти текущей вкладки и сбрасываются при перезагрузке. Серверные гарантии и SQLite относятся к локальному запуску, описанному выше.

Сборка: `python scripts/build_demo.py`. Проверка адаптера: `node --test demo/demo.test.mjs`.

### Устойчивые ограничения запросов

Бюджеты попыток сохраняются в SQLite и разделяются всеми процессами, использующими одну БД. Перезапуск сервера не сбрасывает лимиты. Ответ 429 содержит Retry-After. Для нескольких узлов требуется общая служба ограничений.

### Остатки

Заказ атомарно уменьшает products.stock; при нехватке любого товара откатывается весь заказ. Повтор с тем же ключом не списывает остаток повторно. В новой демонстрационной БД остаток каждого товара — 100. В существующей БД он остаётся NULL до инвентаризации: заказы таких товаров возвращают 409. Оператор задаёт подтверждённые значения в БД до запуска продаж.

### Заказы покупателя и управление складом

Заказ возвращает accessKey. Просмотр требует X-Order-Key: этот ключ; перебор номера заказа не даёт доступа. Интерфейс хранит ключи последних 50 заказов в браузере и позволяет обновить статусы. Не публикуйте ключи и не передавайте их в URL.

Владелец задаёт APP_OWNER_TOKEN (случайный секрет от 32 символов). GET /api/owner/orders и PATCH /api/owner/products/:id/stock требуют Authorization: Bearer. Изменение остатков передаёт stock и expectedStock; устаревшее значение возвращает 409. Для публичного режима задайте APP_PUBLIC_ORIGIN=https://... и TLS-прокси. Старые заказы без ключа доступны владельцу. Доставка исключена из текущего задания.

### Тестовые платежи ЮKassa

Задайте YOOKASSA_SHOP_ID, YOOKASSA_SECRET_KEY (только test_...) и PAYMENT_RETURN_URL (HTTPS). Покупатель создаёт тестовый платёж из «Мои заказы». Сумма берётся из серверного заказа; ключ идемпотентности сохраняется в SQLite. Статус paid устанавливается только после запроса сервером состояния платежа и проверки test, paid, суммы, валюты и связи с заказом. Возврат со страницы оплаты сам по себе заказ не оплачивает. После неопределённого результата старше 23 часов требуется сверка, новый платёж автоматически не создаётся. Рабочие ключи запрещены этим адаптером.


### Кабинет владельца

При серверном запуске откройте `/owner.html`: заказы и остатки. Вход по `APP_OWNER_TOKEN`; ключ не сохраняется в localStorage или URL и удаляется при выходе. На GitHub Pages кабинет не подключён к серверной базе.
